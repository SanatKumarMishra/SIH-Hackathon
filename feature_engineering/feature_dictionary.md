# Feature Dictionary — SIH26186 Feature Engineering Component

Generated by `feature_engineering/pipeline.py` → `data/processed/ml_features.csv`.

All features are computed only from upstream tables: `personnel`, `hr_records`,
`wellness_assessments`, `biometric_data`, `consent_records`. **No feature is
derived from `risk_predictions`, `risk_factors`, or `recommendations`** — these
are downstream model outputs and are actively blocked from being loaded as
feature inputs (`feature_engineering/load_data.forbid_downstream_tables`).

## Engineered features

### `workload_score`
- **Source columns:** `hr_duty_hours`, `hr_deployment_days`
- **Formula:** `0.5 * normalize(duty_hours) + 0.5 * normalize(deployment_days)`, min-max scaled to [0, 1]
- **Type:** float, 0-1
- **Purpose:** Single composite signal for organizational workload intensity.
- **Interpretation:** Higher = heavier combined duty + deployment load.
- **Direction of risk:** Higher → higher welfare risk.
- **Limitations:** Normalized against the *current batch*, not a fixed operational scale; re-fit as more data accrues.

### `high_duty_flag`
- **Source columns:** `hr_duty_hours`
- **Formula:** `1 if duty_hours > 12 else 0` (threshold in `config.THRESHOLDS.duty_hours_high`)
- **Type:** binary (0/1)
- **Purpose:** Simple, interpretable rule-style flag for heavy-duty days (mirrors architecture's "Level 1" rule baseline).
- **Direction of risk:** 1 → higher risk.
- **Limitations:** Threshold is a configurable heuristic, not a validated operational limit.

### `extended_deployment_flag`
- **Source columns:** `hr_deployment_days`
- **Formula:** `1 if deployment_days > 15 else 0`
- **Type:** binary
- **Purpose:** Flags prolonged deployment, called out explicitly in the architecture doc as a Level-1 risk trigger.
- **Direction of risk:** 1 → higher risk.
- **Limitations:** Same-day count only; does not (yet) capture *consecutive* days without real history.

### `leave_utilization_gap`
- **Source columns:** `hr_training_load`, `hr_leave_days`
- **Formula:** `training_load - leave_days`
- **Type:** float (can be negative)
- **Purpose:** Proxy for load taken on without corresponding rest/leave.
- **Direction of risk:** Higher (more positive) → higher risk.
- **Limitations:** A coarse proxy; true "leave deviation" needs a personnel-specific leave baseline (per the architecture's "Leave deviation" contributor), unavailable in the single-snapshot dataset.

### `wellness_score`
- **Source columns:** `wellness_mood_score`, `wellness_sleep_score`, `wellness_fatigue_score`, `wellness_stress_score`
- **Formula:** `((mood + sleep) - (fatigue + stress) + 20) / 40`, scaled to [0, 1]
- **Type:** float, 0-1
- **Purpose:** Composite self-reported well-being score.
- **Direction of risk:** Lower → higher risk.
- **Limitations:** Self-report scale; equal-weights all four components.

### `fatigue_index`
- **Source columns:** `wellness_fatigue_score`
- **Formula:** `fatigue_score / 10`
- **Type:** float, 0-1
- **Purpose:** Normalized fatigue signal, kept separate from the composite score for explainability.
- **Direction of risk:** Higher → higher risk.

### `stress_burden`
- **Source columns:** `wellness_stress_score`
- **Formula:** `stress_score / 10`
- **Type:** float, 0-1
- **Purpose:** Normalized stress signal.
- **Direction of risk:** Higher → higher risk.

### `low_mood_flag`
- **Source columns:** `wellness_mood_score`
- **Formula:** `1 if mood_score <= 3 else 0`
- **Type:** binary
- **Purpose:** Flags self-reported low mood for rule-based triage.
- **Direction of risk:** 1 → higher risk.

### `sleep_deficit`
- **Source columns:** `bio_sleep_duration`
- **Formula:** `7.0 - sleep_duration` (7h is the configured recommended baseline)
- **Type:** float (can be negative if they slept more than baseline)
- **Purpose:** Quantifies shortfall against a recommended sleep duration.
- **Direction of risk:** Higher (more positive) → higher risk.
- **Limitations:** **NaN whenever biometric consent is absent** — never imputed to 0, to avoid implying "no risk" when data is simply missing. Only available for personnel who consented to biometric data collection.

### `low_activity_flag`
- **Source columns:** `bio_activity`
- **Formula:** `1 if activity (steps) < 4000 else 0`
- **Type:** nullable binary (NaN if no biometric consent)
- **Purpose:** Flags a low-movement day.
- **Direction of risk:** 1 → higher risk.

### `low_hrv_flag`
- **Source columns:** `bio_hrv`
- **Formula:** `1 if hrv < 50 else 0`
- **Type:** nullable binary (NaN if no biometric consent)
- **Purpose:** Heuristic physiological-strain flag.
- **Direction of risk:** 1 → higher risk.
- **Limitations:** This is a heuristic threshold, not a clinical HRV interpretation, and HRV baselines are highly individual — treat as a coarse signal only.

### `workload_fatigue_interaction`
- **Source columns:** `workload_score`, `fatigue_index`
- **Formula:** `workload_score * fatigue_index`
- **Type:** float, 0-1
- **Purpose:** Captures compounding risk when high workload coincides with high fatigue (explicitly requested interaction feature).
- **Direction of risk:** Higher → higher risk.

### `stress_sleep_interaction`
- **Source columns:** `stress_burden`, `sleep_deficit`
- **Formula:** `stress_burden * normalize(max(sleep_deficit, 0))`
- **Type:** float, 0-1 (NaN if no biometric consent)
- **Purpose:** Captures compounding risk of stress plus insufficient sleep.
- **Direction of risk:** Higher → higher risk.
- **Limitations:** NaN without biometric consent, same as `sleep_deficit`.

### `pressure_index`
- **Source columns:** `workload_score`, `stress_burden`, `fatigue_index`
- **Formula:** `(workload_score + stress_burden + fatigue_index) / 3`
- **Type:** float, 0-1
- **Purpose:** Single interpretable "overall pressure" summary feature.
- **Direction of risk:** Higher → higher risk.
- **Limitations:** An equal-weighted heuristic summary, not a substitute for the trained model's own weighting.

## Temporal features (NOT present in `ml_features.csv` today)

The dataset provides exactly one observation per personnel (2026-08-01), so
genuine rolling/trend features cannot be computed yet. `feature_engineering/temporal.py`
implements the real logic (7/30/90-day rolling means, change, percent change,
trend slope, deterioration flags) and activates automatically once multiple
days of real history exist per personnel (e.g. once served from the live
PostgreSQL database). A clearly-labelled synthetic generator
(`data/synthetic/generate_demo_history.py`) can produce 30 days of demo data
for showcasing the trend UI — its output is never used by the production
pipeline or for model training.

## Explicitly excluded (data-leakage guard)

`risk_predictions`, `risk_factors`, `recommendations` are never read by
`feature_engineering/load_data.py` for feature purposes — `forbid_downstream_tables()`
raises `DataLeakageError` if anything attempts to load them here.
